## Approach: pilot first, then scale with AI

Convert 2-3 real components by hand (or AI-assisted but closely reviewed)
before trusting AI to convert the rest. Those 2-3 components are what teach
you — and the skill — what the actual conversion rules are. Converting
everything blind first and fixing it later is more expensive than getting
the rules right on a small sample.

---

## Phase 0 — R&D (tools)

Before writing any conversion rules, you need to know what you're actually
working with on both ends.

**Tasks:**

- [ ] Inventory the old app: every screen, every Cordova plugin in use
      (camera, geolocation, storage, push, etc.), every AngularJS pattern
      worth noting (services, directives, `$http` calls)
- [ ] Spike a bare Ionic + React + Capacitor project — confirm build/run on
      both a browser target and at least one device/emulator
- [ ] Resolve Cordova → Capacitor plugin equivalents for whatever the
      inventory turned up (Capacitor has official plugins for most common
      cases; some old Cordova plugins may have no direct equivalent and
      need a replacement library)
- [ ] Decide React state approach for this app (Context+hooks vs Zustand vs
      something else) — small decision but affects every component you
      convert after

**Docs to read:**

- Ionic React getting-started guide
- React or Vue or Angular ?!

## Phase 1 — Skill + pilot components

Build the skill _while_ converting the first 2-3 components, not before —
you need real examples to know what the skill should actually say.

**The skill (`ionic-migration` SKILL.md) should contain:**

- AngularJS → React mapping table: `$scope`/controller state → `useState`/
  `useReducer`, `ng-repeat`/`ng-if` → JSX map/conditional rendering,
  `$http` service calls → fetch/axios + your chosen data layer, AngularJS
  services → custom hooks, `ui-router` states → React Router routes
- Your conventions: component file structure, naming, styling approach
  (Ionic's own components vs custom CSS)
- A per-component checklist: identify scope/state/API calls in the old
  controller → identify template directives → propose React equivalent →
  flag anything ambiguous rather than guessing silently

**Tasks:**

- [ ] Pick 2-3 representative components — ideally one simple (display-only),
      one with form/state, one with a native plugin call, so the pilot
      covers the range of patterns you'll hit later
- [ ] Convert the first one mostly by hand — this calibrates your own
      mental model before handing anything to AI
- [ ] Convert the second/third using AI against a draft skill, reviewing
      output line by line
- [ ] Refine the skill's mapping tables based on what AI got wrong or had
      to guess at
- [ ] Only once the skill produces output you don't have to heavily correct,
      consider it ready to scale
- [ ] Try on Signal

---

## Phase 2 — Scaled AI conversion

**Tasks:**

- [ ] Run remaining components through the skill in batches (not all at
      once — review each batch before continuing, so a bad pattern doesn't
      propagate across 20 components before you catch it)
- [ ] Rebuild navigation/routing as React Router
- [ ] Re-implement auth flow against whatever backend API exists/gets built
- [ ] Track parity: every old screen/feature accounted for or explicitly
      dropped, not silently lost

---

## Phase 3 — Docs

**Tasks:**

- [ ] Write up the final mapping tables and conventions as proper
      documentation (this can live as a Fumadocs page alongside this
      roadmap, or fold into the skill itself if it's the only consumer)
- [ ] Document the plugin replacements decided in Phase 0 with reasoning,
      so future-you doesn't re-litigate the same Cordova→Capacitor choices
- [ ] Component inventory doc: old component → new component, conversion
      status, any manual fixes applied post-AI-conversion

---

## Phase 4 — CI/CD

**Skills to pick up:** CI pipeline for a Capacitor app specifically (build
steps differ from a plain web app — native builds need platform tooling)

**Tasks:**

- [ ] Web build pipeline (lint, type-check, test, build) on every push
- [ ] Native build pipeline (iOS/Android via Capacitor) — at minimum on
      merge to main, possibly nightly given native builds are slower
- [ ] Decide hosting/distribution: PWA deploy target, and/or app store
      pipeline if this ships to stores
- [ ] Wire into your existing Gitea instance if self-hosting CI too, or
      pick a hosted runner if native builds need it
