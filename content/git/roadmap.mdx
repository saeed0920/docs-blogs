<Callout type="warn">
Never rewrite shared history unless the team has explicitly agreed. Prefer `git revert` for commits already pushed to a shared branch. Use `git reset` and interactive rebase for local, unpublished history; if a force push is required, prefer `git push --force-with-lease` over `--force`.

## Context

Workshop moves from Git's local data model to safe collaboration and history recovery. Day 1 establishes mental models and daily commands; Day 2 applies them to shared repositories, debugging, and advanced workflows.

Use one repository throughout both days so each exercise builds on earlier commits, branches, conflicts, and remotes.

## Example Workshop Project

Participants work in pairs on a small documentation repository:

1. Create repository and commit an initial README.
2. Develop separate features on branches.
3. Create and resolve a merge conflict.
4. Push branches and review a pull request.
5. Recover an intentional mistake with `restore`, `revert`, or `reset`.
6. Find a deliberately introduced bug with `git bisect`.

## Review Questions

<Accordions>
  <Accordion title="Why teach Git file states before individual commands?">
    Commands become easier to predict when participants understand working tree, staging area, and repository transitions.
  </Accordion>
  <Accordion title="When should a team use revert instead of reset?">
    Use `git revert` for shared history because it creates a new commit without rewriting commits others may already use.
  </Accordion>
  <Accordion title="What should the final project demonstrate?">
    A complete collaboration flow: branching, commits, remote synchronization, review, conflict resolution, and safe recovery.
  </Accordion>
</Accordions>
